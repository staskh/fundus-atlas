# Reporting a benchmark

Every benchmark leaves **two** documents, and they are made in different ways:

```
docs/benchmarks/<slug>-docs.md      how it is configured and run — GENERATED by the run
docs/benchmarks/<slug>-results.md   what came out, and what it means — WRITTEN from the analysis
```

The configuration page states facts the code already knows, so the code writes it. The results page
draws conclusions, and a conclusion is a judgement: it is written by a person reading the
**notebook**, quoting numbers that come from `results/`. Neither is hand-edited prose invented from
nothing, and neither is a table dumped without a reading.

**What only one benchmark's documents say lives in its own file beside this one** — `quality.md`,
and one per benchmark thereafter — and you load that file too.

| Benchmark | Its documents |
| --- | --- |
| Quality | [quality.md](quality.md) |
| Disc and cup | [disc.md](disc.md) |

## 1. Both pages describe the benchmark, not the command line

They cover **what the benchmark declares and what `results/` holds**, never the subset a run
happened to touch. `--dataset mshf` re-measures one dataset; it must not rewrite either page as
though the others had never been measured, and it must not report "1 of 1 datasets took part" when
the benchmark declares six. The same rule covers `docs/BENCHMARKS.md`: running one benchmark must
not blank another's section.

## 2. An existing results page is extended, never replaced

Like a notebook (`analyse-benchmark` §1), the results page accumulates. Sections arrive from
conversation, from a question somebody asked once, from a finding that took an afternoon.

- **A section that exists stays**, under the same heading, even when its content is rewritten from
  new numbers. A reader who bookmarked section 4 should find section 4 still answering the same
  question.
- **New information adds a section or rewrites one**, and says what changed if the conclusion
  moved.
- **Removing a section needs a reason and a sentence saying why it went.** If the analysis behind
  it was superseded, say so in the section rather than deleting it silently.

The configuration page has no such rule: it is generated, it holds no judgement, and it is
rewritten in full every time.

## 3. The results page is compiled from the notebook

The notebook is where the analysis happens; the results page is where its conclusions are stated
for somebody who will not open it. So **read the notebook's output and write from it** — not from
the raw CSVs, and not from the summary JSONs alone.

- Every number quoted must be one the notebook or `results/` actually produced. Re-deriving a
  figure by hand is how a document comes to disagree with its own evidence.
- Where the notebook shows something the tables do not — two populations behind one mean, a camera
  that behaves unlike its neighbours, a reference the readers themselves could not agree on — that
  belongs here, in prose, with the notebook named as where to see it.
- Where the notebook shows nothing conclusive, say that. "No difference worth reading" is a result.

## 4. The shape of the results page

1. **A table of contents**, first, always. These pages run long and a reader arrives looking for one
   thing.
2. **A summary that stays summary.** One table, **all datasets pooled**, one row per model — the
   handful of numbers that matter for this benchmark, and nothing else. Detail belongs further
   down; a reader who wants per-dataset rows will scroll to them.
3. **The detail**, dataset by dataset and then by subset and split, for the reader who got to
   section 2 and wanted more. Where a dataset's splits carry different contamination marks, the
   breakdown is required rather than optional.
4. **What the analysis found** — the conclusions, from the notebook, in prose.
5. **A recommendation**, per section 5.
6. **What these numbers do not say** — the marks, the references that are not comparable, the
   assumptions the run rests on.

**The model is the primary index in every table**, and the dataset, split or kind the secondary
one, so that the page and the notebook can be read against each other.

## 5. Name the best model, and say what "best" means

A reader's question is "which should I use", and refusing to answer it is not neutrality — it is
leaving the judgement to whoever reads the table fastest. So **say which model performs best**, and
with it:

- **the question it is best at** — agreement with the readers as shipped, ranking photographs,
  coverage — because the answer changes with the question, and where it changes, say so;
- **the second, whenever it is close**, with the margin. Two models a hundredth apart are not
  ordered by that hundredth;
- **the caveats that would change the answer**: a contamination mark, a threshold set on other
  data, a dataset whose reference is assumed rather than published.

What is still forbidden is a bare ordering: a column sorted by score with no statement of what the
score answers, no margin, and no caveat. A recommendation is an argument, and an argument can be
disagreed with — which is the point.

## 6. `<slug>-docs.md` — how it is configured

Generated, before the measuring starts, and again whenever the benchmark's code changes. Numbered
sections, in this order:

1. **What this benchmark asks.**
2. **Which models take part** — the page each links to, the pinned commit or version, the store grid
   it reads, the grid its network sees, its ensemble size, what it emits. **Every declared model
   appears, including ones that did not run**, with the reason.
3. **Which datasets take part** — photographs, where the reference grade comes from, what was set
   aside and why. **Every declared dataset appears**, marked *no store built* or *excluded whole*.
4. **What is excluded, and by which rule.**
5. **How to run it** — the command, its options, how to re-measure one pair, what a sampled run is.
6. **What each column of the result CSV means** — every column, including the ones a model leaves
   absent and why.
7. **What a re-run repeats** — the fingerprint, and the separate question of completeness.
8. **The three counts** — `processed`, `total`, `excluded` with its reasons — and that our
   `excluded` and a model's `declined` are never added together.

A column added to the evidence that section 6 does not explain is a bug, and so is a model added to
the run that section 2 does not list.

## 7. What both documents must always carry

- **The contamination mark on every result**, never aggregated away, and `unknown` never written as
  if it were `out-of-sample`.
- **The pins**: a number with no commit behind it is an anecdote.
- **Coverage beside every accuracy**, never folded into it.
- **A dash for a metric that does not exist** — never a zero, never an omitted row.
- **A partial run says so**, in the first paragraph and in every table it touches, with how many of
  the dataset were scored out of how many it holds.
- **A run missing a declared piece says so**, with how many models of how many declared.

## 8. What they must never do

- **Restate an author's claim as ours**, or ours as theirs.
- **Average across datasets without saying so.** The pooled summary of section 4.2 is an average,
  and the page says which datasets went into it and that the detail is below.
- **Explain away a bad number.** If a result needs an argument, make the argument — with the
  evidence — or leave the number alone.
- **Quote a figure nothing produced.**

## 9. Prose

Written for a clinician or a researcher (`CLAUDE.md` §4.1): every metric expanded on first use, no
jargon assumed, and the reason a number matters stated before the number.
